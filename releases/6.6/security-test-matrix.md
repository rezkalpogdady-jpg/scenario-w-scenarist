# مصفوفة اختبارات أمن منصة سيناريو وسيناريست — المرحلة 6.6

## الغرض
هذه المصفوفة تحدد اختبارات القبول المطلوبة قبل اعتبار حماية المنصة مكتملة أو دمج أي تغيير في `main`. لا تفترض أن وجود فحص RLS أو نجاح فحص JavaScript يعني نجاح الاختبارات الأمنية.

## الأدوار
- **زائر (anon):** غير مسجل الدخول.
- **عضو A:** حساب موثق عادي.
- **عضو B:** حساب موثق مختلف عن A.
- **مدير:** حساب موثق يحمل `app_metadata.role = admin` من مصدر موثوق في Supabase Auth.

## اختبارات Storage

| الاختبار | النتيجة المطلوبة |
|---|---|
| anon ينشئ Signed URL أو ينزّل ملفًا من member-submissions | ممنوع |
| عضو A يقرأ ملف عضو B من member-submissions | ممنوع |
| عضو A يرفع ملفًا خارج مجلده الذي يبدأ بـ UUID الخاص به | ممنوع |
| عضو A يحذف ملفًا مرتبطًا بطلب قائم | ممنوع |
| عضو A يرفع ملفًا أكبر من 25 MiB أو MIME غير مسموح | ممنوع من جهة Storage، لا الواجهة فقط |
| المدير ينشئ رابطًا مؤقتًا للمراجعة | مسموح |
| الملف لا ينتقل إلى site-media قبل الاعتماد | مطلوب |
| فشل إدخال سجل العمل بعد رفع الملف | تتم إزالة الملف اليتيم أو تسجيل مهمة تنظيف موثوقة |

## مراجعة الدوال ذات الامتيازات
لكل دالة `SECURITY DEFINER`:
1. التأكد من وجود تحقق صريح من دور المدير داخل جسم الدالة، وليس في JavaScript فقط.
2. تثبيت `search_path` آمن أو استخدام أسماء مؤهلة بالكامل للكائنات.
3. حصر `EXECUTE` على الأدوار اللازمة عبر GRANT/REVOKE.
4. التحقق من أن معرف السجل ومدخلات الحالة والروابط لا تسمح بتجاوز ملكية السجل.
5. التأكد من عدم تسريب بيانات حساسة في رسائل الأخطاء أو النتائج.

الدوال التي يستدعيها التطبيق وتحتاج مراجعة: `admin_review_member_work`, `admin_review_member_profile`, `admin_review_community_submission`, `admin_visit_stats`, `join_chess_game`, `submit_chess_position`.

## نقاط فنية ظهرت من مراجعة الواجهة
- تحقق `app_metadata.role` في المتصفح حاجز عرض فقط؛ RLS والدوال المخزنة هي حدود الأمان الحقيقية.
- يستخدم التطبيق جداول متعددة مباشرة، لذلك يجب تدقيق كل جدول في الاستعلامات، وليس `member_profiles` و`member_works` فقط.
- بطاقات الراديو والتليفزيون تستخدم معرّفات قاعدة البيانات داخل معالجات `onclick` مضمّنة. المعرفات الحالية تأتي من سجلات المحتوى، لكن الأفضل نقلها إلى `data-*` ومعالجات أحداث مفوضة لتجنب إدخال بيانات ديناميكية في سياق JavaScript داخل HTML.
- روابط البث يجب أن تحمل بيانات مصدر وترخيص وحالة تحقق قبل النشر؛ فقبول رابط HTTP/HTTPS وحده لا يثبت أن البث مرخص أو صالح.
- مسارات Storage العامة يجب ألا تُستخدم لملفات الأعضاء الخاصة قبل موافقة الإدارة.

## ما تم وما لم يتم
- تم حفظ هذا المستند كخطة اختبار قبول.
- نجح GitHub Actions في فحص JavaScript المضمن وفحص أنماط مفاتيح الخادم على الفرع `stage/6.6-platform-audit` في التشغيل رقم 5.
- لم تُنفذ اختبارات الأدوار ضد Supabase؛ لم يتم توصيل بيئة قاعدة البيانات بهذه الجلسة.
- لم يتم تشغيل أي Migration، ولم يتم تغيير `main`.
- لا يجوز وضع علامة "آمن/مكتمل" قبل تنفيذ الاختبارات أعلاه وتوثيق نتائجها.

## ترتيب التنفيذ
1. تشغيل `preflight-6.5-readonly.sql` وتصدير النتائج دون مشاركة مفاتيح أو بيانات شخصية.
2. مراجعة السياسات الحالية وامتيازات PUBLIC وanon وauthenticated.
3. مراجعة أجسام الدوال الحساسة وإعدادات `SECURITY DEFINER`.
4. إعداد Migration متوافق مع المخطط الفعلي بعد مراجعة النتائج.
5. اختبار السيناريوهات باستخدام حسابات اختبار منفصلة، ثم توثيق النتائج.
