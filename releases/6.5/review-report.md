سيناريو وسيناريست – المرحلة 06 – تحديث 6.5
العنوان: مراجعة الصلاحيات وحماية ملفات الأعضاء

الأساس:
- بُني التحديث على حزمة 6.4 المحفوظة، دون تعديل أو استبدال ملفات 6.4 الأصلية.
- ملف HTML واجهة تراكمية مبنية على 6.4؛ لا توجد إعادة تصميم أو تغيير في وظائف الواجهة.
- ملف SQL Migration مستقل وإضافي، لا يحذف بيانات أو سجلات أو ملفات.

التغييرات:
1. إضافة سياسات RLS تقييدية لقراءة وإنشاء وتحديث ملفات الأعضاء.
2. تأكيد أن العضو لا يقرأ إلا ملفه الشخصي أو الملفات المعتمدة، مع صلاحية الإدارة للقراءة والمراجعة.
3. منع التعديل والحذف المباشر لسجلات أعمال الأعضاء من حسابات anon/authenticated؛ الإرسال الجديد فقط بحالة pending.
4. تأكيد خصوصية bucket member-submissions وحد 25 MiB وأنواع الملفات المعتمدة.
5. إضافة سياسات تقييدية على storage.objects لمساحة member-submissions لمنع توسيع الوصول عبر سياسات permissive أخرى.
6. الإبقاء على مسار اعتماد الإدارة الموجود في 6.4 ودالة admin_review_member_work المحمية.

الفحوصات المنفذة محليًا:
- مراجعة مصدر HTML وSQL في حزمة 6.4 قبل التعديل.
- التحقق من وجود سياسات RLS الحالية ودالة اعتماد أعمال الأعضاء.
- التحقق النصي من عدم وجود مفاتيح service_role أو أسرار في ملفات التسليم.
- التحقق من وجود الملفات الأربعة داخل حزمة 6.5.

حدود التحقق:
- لم يتم تنفيذ SQL على مشروع Supabase الحي.
- لم يتم إجراء اختبار دخول فعلي بحساب عضو أو مدير أو زائر.
- لم يتم اختبار رفع/قراءة/حذف الملفات على Storage الحي.
- لذلك تُعد الحزمة جاهزة للمراجعة والتنفيذ المرحلي، وليست اعتمادًا أمنيًا نهائيًا قبل الاختبارات الحية.

الاختبارات المطلوبة بعد التنفيذ:
A) عضو لا يقرأ ملف عضو آخر غير المعتمد أو أعماله.
B) زائر لا يقرأ ملفات member-submissions.
C) العضو لا ينشئ عملًا معتمدًا ولا يعدّل أو يحذف سجل عمل قائمًا.
D) العضو يرفع ويقرأ ملفه داخل مجلده فقط.
E) لا يمكن حذف ملف مرتبط بطلب قائم.
F) المدير يراجع الأعمال ويصدر Signed URL مؤقتًا.
G) العمل المعتمد فقط ينتقل إلى مساحة النشر العامة.

القرار:
تحديث 6.5 مكتمل كحزمة ملفات مستقلة. لا تُستبدل النسخ السابقة. لا تُلصق النسخة الجديدة على الموقع قبل حفظ نسخة نشر احتياطية وتنفيذ SQL ثم اجتياز اختبارات الحسابات والملفات.
