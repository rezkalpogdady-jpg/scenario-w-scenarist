# دليل الفحص الحي قبل اعتماد منصة سيناريو وسيناريست — 6.8

**الحالة:** إعداد خطوات التحقق فقط. لم يتم الاتصال بقاعدة Supabase أو تشغيل SQL أو اختبار متصفح حي.

## تنبيه قبل البدء
- لا تشغّل `releases/6.5/migration.sql` الآن.
- لا تشغّل `releases/6.6/member-profile-review-trigger.sql` الآن.
- لا تنفذ CREATE أو ALTER أو GRANT أو REVOKE أو أي تعديل بيانات.
- سبب التوقف: سبق أن ظهر الخطأ `42P01: relation "public.member_profiles" does not exist` عند محاولة تحديث 6.5. يجب فهم حالة المخطط الحي أولًا، وعدم إعادة تشغيل Migration على التخمين.

## أ) فحص Supabase للقراءة فقط
من لوحة Supabase للمشروع والفرع الصحيحين:

1. افتح SQL Editor وتأكد أن المشروع/الفرع المقصود هو نفسه الذي ستختبر عليه الموقع.
2. افتح الملف `releases/6.8/preflight-65-dependencies-readonly.sql` وانسخ محتواه كما هو.
3. راجع أنه فحص قراءة فقط، ثم شغّله مرة واحدة واحفظ كل مجموعات النتائج، خصوصًا وجود `member_profiles` و`member_works` والأعمدة المطلوبة وbucket `member-submissions` ودوال Storage اللازمة.
4. افتح الملف `releases/6.8/preflight-admin-data-access-readonly.sql` وانسخ محتواه كما هو.
5. شغّله للقراءة فقط واحفظ كل النتائج: وجود الجداول، RLS وFORCE RLS، امتيازات anon/authenticated، سياسات الجداول والتخزين، إعدادات buckets، تعريفات RPC وامتيازات EXECUTE، والـ Triggers.
6. لا تُعد تشغيل أي Migration بناءً على نتيجة منفردة. أرسل النتائج كاملة للمراجعة أولًا.

## ب) قواعد اتخاذ القرار بعد النتائج
- إذا كان جدول أو عمود مطلوب مفقودًا: توقف؛ لا تشغّل Migration 6.5 ولا تنشئه يدويًا قبل مطابقة المخطط الكامل مع النسخة الحالية.
- إذا كان RLS غير مفعّل أو توجد امتيازات واسعة: لا تغيّرها مباشرة؛ نحدد السياسة المطلوبة ونراجع أثرها قبل أي تعديل بموافقة صريحة.
- إذا غاب `scenario_scripts` أو bucket `scenario-scripts`: لا تنشئهما تخمينًا؛ نحتاج المخطط المقصود ونتائج الفحص أولًا.
- راجع أجسام RPC الثلاث: `admin_review_member_profile` و`admin_review_member_work` و`admin_review_community_submission`. يجب أن تتحقق الدوال من دور المدير داخل قاعدة البيانات، وليس اعتمادًا على إخفاء لوحة الإدارة في JavaScript.

## ج) اختبار المتصفح بعد مراجعة نتائج Supabase
استخدم حسابات تجريبية فقط، ولا تستخدم ملفات أو بيانات شخصية حقيقية:

1. **زائر anon:** يتصفح المنشور فقط، ولا يقرأ ملفات الأعضاء الخاصة أو يفتح PDF خاصًا.
2. **عضو A:** ينشئ ملفًا وعملًا تجريبيًا؛ يظل الملف الشخصي والعمل pending قبل الموافقة.
3. **عضو B:** يحاول قراءة وتعديل سجل A وملفه؛ يجب أن تُرفض المحاولات من قاعدة البيانات، لا من الواجهة فقط.
4. **مدير:** يراجع الملفات عبر RPC، وينشر محاضرة ثم يتأكد من تحديث العرض العام فور الحفظ دون إعادة تحميل الصفحة.
5. **مكتبة السيناريوهات:** anon لا يحصل على PDF؛ عضو مسجل يقرأ العمل المنشور عبر Signed URL مؤقت؛ العضو العادي لا يغيّر published ولا يحذف السجل؛ المدير وحده يدير المكتبة.
6. سجّل النتيجة الفعلية ورسالة الخطأ لكل اختبار في `member-admin-manual-test-checklist.md`.

## د) ما الذي يُعد نجاحًا؟
- نجاح CI يثبت الفحوص البرمجية الساكنة فقط.
- لا تعتبر حماية قاعدة البيانات مكتملة حتى تظهر نتائج preflight سليمة وتنجح اختبارات anon وعضو A وعضو B والمدير على البيئة الفعلية.
- لا دمج إلى main ولا نشر قبل مراجعة النتائج وإغلاق حالات الفشل.
